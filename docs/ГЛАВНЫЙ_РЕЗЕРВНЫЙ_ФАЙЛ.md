# «Двое» — ГЛАВНЫЙ РЕЗЕРВНЫЙ ФАЙЛ

Проект «Живая рука». Обновлено: 3 октября 2026.
С этим файлом и резервной копией проект можно восстановить и продолжить **без Claude** — с любым другим помощником или разработчиком.

В этом файле нет паролей, ключей и секретных кодов. Он лежит в публичном репозитории (`docs/ГЛАВНЫЙ_РЕЗЕРВНЫЙ_ФАЙЛ.md`) — личного сюда не писать.

## 1. Главное за минуту

- Приложение, сайт и база **не зависят от Claude**. Если доступ к Claude пропадёт, у тебя и партнёрши всё продолжит работать.
- От Claude зависит только разработка: чаты, документы ТЗ и макеты. Тексты ТЗ лежат в репозитории (`docs/TZ_*.md`), итоги этапов — в `docs/PROGRESS_*.md`.
- Весь код и вся история — на GitHub. **Автоматическая копия** всех веток — в приватном репозитории `kotpek31-cell/dvoe-backup` (обновляется при каждом изменении, см. раздел 6).
- Данные (записи дневника, вещи, роли, отпечатки кодов) и аккаунты (почты и хеши паролей) — в Supabase. **Автоматическая копия** раз в сутки, последние 14 — в том же приватном репозитории, ветка `db-dumps`.

## 6. Автоматическая копия (`backup.yml`)

| Что | Когда | Куда |
| --- | --- | --- |
| Все ветки и теги | при каждом push в любую ветку, где уже есть `backup.yml`, и раз в сутки | `dvoe-backup`, те же имена веток |
| База: схемы `public` и `private` (pg_dump, структура и данные) — файлы `dvoe_ДАТА.sql.gz` | раз в сутки в 03:23 по Москве и по кнопке Run workflow | `dvoe-backup`, ветка `db-dumps`, последние 14 |
| Аккаунты: данные `auth.users` и `auth.identities` (почты, хеши паролей, способы входа) — файлы `auth_ДАТА.sql.gz` | вместе с базой | там же, последние 14 |

- `main` копируется только вперёд: если его историю перепишут, копия не затрётся, а запуск станет красным — это сигнал разобраться.
- Удалённые ветки в копии остаются.
- Аккаунты входят в копию отдельным файлом `auth_…`: только данные двух таблиц, структуру схемы `auth` создаёт сам Supabase. Пароли — хеши, сами пароли не узнать, но после восстановления люди входят со своими почтой и паролем. Файл с той же датой, что у `dvoe_…`, — из одного запуска, восстанавливать их парой.
- Расписание и кнопка Run workflow работают только из `main`; копия веток при push — из любой ветки, где есть `backup.yml`.
- Секреты в репозитории `dvoe` (Settings → Secrets and variables → Actions): `BACKUP_TOKEN`, `SUPABASE_DB_URL`. В логах Actions их нет, дамп с личными данными уходит только в приватный репозиторий.
- В `dvoe-backup` выключены Actions (иначе скопированные workflow начнут там запускаться).
- Проверка: `github.com/kotpek31-cell/dvoe/actions/workflows/backup.yml` — последний запуск зелёный.

**Вручную, на компе** (если автоматика не работает), нужен PostgreSQL 17 и строка подключения Session pooler из Supabase (кнопка Connect):

```
pg_dump "СТРОКА_ПОДКЛЮЧЕНИЯ" -n public -n private --no-owner | gzip > dvoe_данные.sql.gz
pg_dump "СТРОКА_ПОДКЛЮЧЕНИЯ" --data-only -t auth.users -t auth.identities --no-owner | gzip > auth_аккаунты.sql.gz
```

В файле личные записи и отпечатки кодов — никому не отправлять и не класть в публичный репозиторий.

## 7. Как восстановить

### Код пропал с GitHub или закрыт доступ к репозиторию `dvoe`

1. Возьми код из `dvoe-backup` (там все ветки) или из `dvoe-вся-история.bundle`: `git clone dvoe-вся-история.bundle dvoe`, затем `cd dvoe` и `git checkout main`.
2. Создай новый репозиторий на GitHub и отправь туда: `git remote set-url origin НОВЫЙ_АДРЕС`, затем `git push --all`
3. В репозитории включи Settings → Pages → Source: GitHub Actions. Сайт соберётся сам.
4. Если адрес сайта изменился, поправь `vapid_subject` в `private.app_config` и адрес в `CLAUDE.md`.
5. Если поменялось имя репозитория — поправь проверку `github.repository` в `backup.yml` и заведи секреты заново.

### База пропала (вместе с аккаунтами)

Порядок важен: **аккаунты → данные → schema.sql**. Аккаунты нужны раньше данных (таблицы приложения ссылаются на `auth.users`), а `schema.sql` — после (он создаёт триггер «новый пользователь → профиль»; если он будет при загрузке аккаунтов, профили задвоятся).

Всё ниже — **на компе**, нужен PostgreSQL 17 (`psql`).

1. Создай новый проект Supabase (Postgres 17, лучше тот же регион eu-north-1). Ничего в нём не запускай — ни `schema.sql`, ни SQL Editor.
2. Возьми строку подключения: кнопка **Connect** → Session pooler (порт 5432), подставь пароль базы. Дальше — `URL`.
3. Скачай из `dvoe-backup`, ветка `db-dumps`, пару файлов с **одной датой**: `auth_ДАТА.sql.gz` и `dvoe_ДАТА.sql.gz`.
4. **Аккаунты:**
   ```
   gunzip -c auth_ДАТА.sql.gz | psql "URL" --single-transaction -v ON_ERROR_STOP=1 -c "SET session_replication_role = replica" -f -
   ```
   Если `SET session_replication_role` не разрешён — та же команда без `-c "…"`: на пустом проекте триггеров на `auth.users` ещё нет.
   Если ругается на столбец, которого нет (Supabase обновил таблицы входа), — пришли ошибку помощнику: нужно убрать этот столбец из строки `COPY` в файле.
5. **Данные приложения:**
   ```
   gunzip -c dvoe_ДАТА.sql.gz | psql "URL"
   ```
   Строки `schema "public" already exists` и подобные про уже существующее — не страшно. В конце проверь: `psql "URL" -c "select count(*) from public.profiles"` — столько же, сколько людей.
6. **Достройка:** в SQL Editor выполни `supabase/schema.sql` целиком («Run without RLS»). Он не трогает данные, но возвращает то, чего нет в дампе: триггер на `auth.users`, правила закрытого канала комнаты (`realtime.messages`), публикацию realtime, права. `catalog.sql` и `patch_*.sql` не нужны — вещи и всё остальное уже в данных.
7. Разверни функцию `push` из `supabase/functions/push/index.ts` с выключенной проверкой JWT.
8. Впиши новый адрес и ключ проекта в `.env` (и переменные репозитория), поправь `push_url` в `private.app_config`, обнови секрет `SUPABASE_DB_URL` в `dvoe`.
9. Authentication → Providers → Email: выключи Confirm email (как было).
10. Выпусти сайт и обновление Android с новым `.env`. Все войдут заново **своими почтой и паролем** — старые сессии не перенесутся. Роли, вещи, записи и отпечатки кодов уже на месте; секретные коды заново заводить не нужно.

Если копии аккаунтов нет (старый дамп без `auth_…`): шаг 4 пропусти — без аккаунтов записи не привяжутся к людям: всем придётся зарегистрироваться заново, а владельца назначить по новому ID.

### Нужен новый APK

- Через сайт expo.dev: проект `dvoe` → Builds → новый билд, профиль `preview`, ветка `main`.
- Или в Codespace: `eas build -p android --profile preview`.
- Обновление без нового APK: `eas update --channel preview`.
- Новый APK нужен, когда меняются нативные файлы: иконка приложения (в этапе фиксации — фон-аврора и монохромная иконка), новые нативные модули, версия в `app.json`.

## 8. Как продолжить работу без Claude

Любому помощнику или разработчику дай три вещи: репозиторий (или копию из `dvoe-backup`), `CLAUDE.md` и последний `docs/PROGRESS_*.md` с `docs/TZ_*.md`. Первое сообщение:

```
Это проект «Двое» (Expo + Supabase). Прочитай CLAUDE.md, docs/PROGRESS_3.0.md, docs/PROGRESS_0.2_FIX.md и docs/FIX_0.2.md (раньше — docs/PROGRESS_0.2.2.md и docs/TZ_0.2.2.md) — там всё о проекте, правила работы и текущее состояние. Продолжаем с этапа, который указан в PROGRESS как следующий.
```

Доступы к Supabase и Expo у другого помощника придётся настроить заново или делать эти шаги руками по разделу 7 в `CLAUDE.md`.

## 9. Порядок «Живая рука»: что делать после каждого этапа

Сессия разработки делает сама (правило записано в `CLAUDE.md`, раздел 6):

1. Обновляет `docs/PROGRESS_*.md` и этот файл: дата, состояние версий и веток, что изменилось в инфраструктуре и в шагах восстановления.
2. Сохраняет в `docs/` полный текст ТЗ текущей версии и ссылки на макеты.
3. Отправляет всё в GitHub.
4. Проверяет, что последний запуск `backup.yml` прошёл успешно.
5. Присылает тебе этот файл.

Ты делаешь:

1. Сохраняешь присланный файл в папку «Живая рука».
2. Раз в месяц и перед выпуском — заглядываешь в `dvoe-backup`: есть свежие ветки и файлы в `db-dumps`.
3. Следишь за сроком `BACKUP_TOKEN` (раздел 4).
